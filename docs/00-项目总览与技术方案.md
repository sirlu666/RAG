# 00 · 项目总览与技术方案

## 1. 目标与非目标

### 目标（答辩时能演示、能量化的四件事）
1. **有据可查**：每个解答附检索片段 + 来源（文档名 / 页码 / 章节），可点击回看原文。
2. **答得对**：在自建数学测试集上，检索 Recall@5 ≥ 0.85，答案正确率 ≥ 0.80（人工抽检 50 题）。
3. **数学友好**：LaTeX 全链路正确渲染（`$...$` / `$$...$$`），公式在切片、检索、生成、展示四步中不被割裂。
4. **可运营**：用户能自建知识库、增量更新文档、删除后不留脏数据。

### 非目标（明确砍掉，避免范围失控）
- 不做模型微调（SFT/LoRA）—— 成本高、三人组时间不够，且与"可溯源"目标正交。
- 不做多轮工具调用 Agent（画图、计算器）—— 列为"未来工作"。
- 不做 K12 全学科 —— 只做**高中数学 + 高等数学（微积分/线代）** 两个学科包。
- 不做移动端 App —— 响应式 Web 足够。

## 4. 技术选型与理由

| 层 | 选择 | 为什么 | 备选（不选的原因） |
|---|---|---|---|
| 前端框架 | Vue 3 + Vite + TS | 生态熟、Element Plus 组件全、构建快 | React（团队更熟 Vue） |
| 公式渲染 | **KaTeX** | 同步渲染、速度快、SSR 友好 | MathJax（更全但慢，按需可加 `mhchem` 扩展） |
| Markdown | markdown-it + shiki/highlight.js | 可控插件链，能拦公式 | 直接 v-html（XSS 风险） |
| 流式传输 | **SSE**（`text/event-stream`） | 单向下行足够、浏览器原生重连、Nginx 一行配置、比 WebSocket 好调试 | WebSocket（仅当需要"生成中打断/多路复用"才值得，P4 可选做中断按钮） |
| 后端 | FastAPI | 异步、Pydantic 校验、自动 OpenAPI（直接当契约用） | Flask（无原生异步与 schema） |
| 向量库 | **Chroma（PersistentClient）** | 零运维、支持 metadata where 过滤、Python 原生 | Milvus（重）、FAISS（无元数据过滤） |
| 检索 | BM25 + 向量 → RRF 融合 → Rerank | 数学题干含大量符号/术语，纯向量会漏精确匹配 | 纯向量（召回不稳） |
| Embedding | bge-m3（API 或本地） | 中英混合 + 数学术语表现好，1024 维 | text-embedding-3-small（中文数学稍弱、要外网） |
| Rerank | bge-reranker-v2-m3 | 交叉编码器，Top-20 → Top-5 提升明显 | 不 rerank（Top-K 噪声大） |
| 大模型 | DeepSeek-chat | 中文强、便宜、OpenAI 兼容、支持流式 | GPT-4o（贵）、本地 Qwen（显存不够） |
| DB | SQLite → PostgreSQL | 开发零配置；上线切 PG 只改连接串 | 直接上 PG（本地开发麻烦） |
| 部署 | Docker Compose + Nginx | 一台机器搞定，答辩现场可离线演示 | K8s（过度设计） |

## 5. 两条核心链路

### 5.1 入库链路（A 主导，B 提供 embedding 接口）

```
上传文件 → 落盘（uuid 命名）→ 创建 document(status=pending)
        → 异步任务：解析(PDF/DOCX/MD) → 清洗(去页眉页脚/断行修复)
        → 结构化识别(知识点/例题/习题 段落) → 公式保护切分
        → 生成 chunk + metadata → 批量 embedding
        → 写入 Chroma + 写 chunks 表 → 更新 document(status=ready, chunk_count)
失败 → status=failed + error_msg（前端可见，可重试）
```

### 5.2 问答链路（B 主导，C 消费）

```
用户提问(+可选图片) → [图片走 OCR → 得到题干文本，用户可编辑确认]
  → query 改写(多轮时：结合历史补全指代)
  → 并行：BM25 Top-20 ｜ 向量 Top-20（metadata 过滤：user_id + kb_ids + 学科）
  → RRF 融合 → Rerank → Top-5
  → 置信度判定：最高分 < 阈值 → 走"未检索到依据"兜底回复（不硬编）
  → Prompt 组装(System + Few-shot + 检索片段 + 历史 + 问题)
  → DeepSeek 流式 → SSE 推送 delta
  → 结束：推送 citations + 相似题 + token 统计
  → 落库：messages(含 citations JSON)
```

## 6. 关键架构决策（ADR）

### ADR-01 全部 chunk 放**一个** Chroma collection，用 metadata 过滤，而不是"每文档一个 collection"
- 理由：collection 数量会随文档线性膨胀，删除/重建/跨库检索都变复杂；Chroma 的 `where` 过滤性能足够。
- 约定：`metadata = {user_id, kb_id, doc_id, chunk_type, subject, grade, kp_ids, difficulty, page, seq}`。详见 `01` §3。

### ADR-02 切片按"知识点—例题—习题"结构化切分，而不是固定 500 字
- 数学内容的最小语义单元是**一道完整例题**，切断题干与解答会让检索命中但生成错乱。
- 策略：先按标题/编号正则识别块 → 块内超过 800 token 再递归切 → 公式与上下文用 overlap 保护。
- 兜底：识别失败时退化为 `RecursiveCharacterTextSplitter(800, 120)`，分隔符优先级 `\n\n$$`、`\n\n`、`。`、`\n`。

### ADR-03 混合召回 + RRF，而不是单纯向量
- 用户提问常含 `f(x)=x^2+2x` 这类精确符号，BM25 对符号串命中率高；向量补语义（"求导"≈"导数计算"）。
- RRF（k=60）无需归一化分数，工程上最省事；之后再接 rerank 精排。

### ADR-04 流式用 SSE
- 生成是单向的，不需要 WebSocket 的双工；SSE 断线自动重连、Nginx 只需 `proxy_buffering off`。
- 代价：无法中途"打断"。若 P4 有余力，加 `POST /api/chat/{id}/stop` 用服务端 flag 实现。

### ADR-05 解析用 FastAPI BackgroundTasks，不引入 Celery/Redis
- 单机、低并发（答辩 3-5 人同时用），BackgroundTasks 足够；任务状态存 DB，前端轮询或订阅 SSE。
- 若并发上传 > 10，再把任务抽到 RQ，接口不变（这就是先定契约的好处）。

### ADR-06 引用可溯源到"页码 + 字符偏移"
- chunk 落库时保存 `page`（PDF 页码）与 `char_start/char_end`，前端"原文跳转"才能定位到段落而不是只给个文件名。

### ADR-07 检索不到就拒答
- 数学场景编造的代价极高。设 `top_score < 0.35` 或 rerank 后无相关 → 返回"未在知识库中找到依据，以下是通用解法（不保证与教材一致）"并显式标注来源类型。

## 7. 降级与容错

| 故障 | 表现 | 降级动作 |
|---|---|---|
| DeepSeek 超时/限流 | 首 token > 10s | 指数退避重试 2 次 → 切备用模型（如 Qwen 兼容口）→ 返回"服务繁忙" |
| Embedding 服务不可用 | 入库卡住 | 切本地 bge-small-zh（慢但可用），任务标 `degraded` |
| OCR 失败 | 图片无文字 | 返回可编辑文本框，让用户手输题干 |
| Chroma 文件损坏 | 检索报错 | 提供 `scripts/rebuild_index.py` 从 chunks 表重建 |
| 前端 SSE 断流 | 消息中断 | 自动重连 + `last_event_id` 续传；UI 显示"重新生成" |

## 2. 答辩必问 12 题 · 参考答法

**Q1 为什么要 RAG，不直接微调？**
微调解决"说话风格/领域语感"，不解决"知不知道这本教材第 132 页怎么写的"。本项目核心诉求是可溯源、可更新、低成本：RAG 换一份教材只要重新入库，微调要重训；且数学答案需要引用原文作为可信依据，微调的参数里拿不出引用。

**Q2 你怎么证明检索有效？**
自建 80 题测试集（问题 + 标准答案 + 依据 chunk_id），指标 Recall@5、MRR；做了消融：纯向量 → +BM25 混合 → +Rerank 三档（填真实数字）。评估脚本可复现：`temperature=0`、跑 3 次取均值、配置落在 `eval_runs.config`。

**Q3 chunk 大小怎么定的？**
不是拍的。做了 300/500/800 三档对比实验，Recall@5 分别为 …，最终选 500±200，并且因为数学的语义单元是"一道例题"，采用结构化切分优先、长度切分兜底。

**Q4 混合召回怎么融合分数？**
用 RRF（Reciprocal Rank Fusion, k=60），只依赖排名不依赖分数尺度，避免 BM25（0-20 分）与余弦（0-1）量纲不一致的问题；融合后再用 bge-reranker 精排 Top-20。

**Q5 怎么防止模型胡说？**
四层：① 检索门槛（top score < 阈值直接拒答）；② Prompt 约束（只能基于片段、必须标引用、公式用 LaTeX）；③ 后处理校验（答案中 `[n]` 必须存在）；④ 前端展示引用片段并可跳原文，用户能自查。

**Q6 多轮对话怎么做的？**
只做"上下文窗口"：同会话带最近 3 轮进 prompt，控制 token；不做指代消解模型，因为成本（18h）与收益不成比例。如果追问出现"这一步"，提示用户把上一步的式子贴上——宁可让交互退一步，也不引入一个不准的改写模型。

**Q7 系统并发能力如何？**
单机 2C4G，SSE 长连接 5 并发下首 token P95 ≈ …ms，端到端 ≈ …s。瓶颈在大模型 API 而非本地；本地检索 < 300ms。单进程（`--workers 1`）+ 单写入者是刻意设计，见 00 §7。

**Q8 为什么不做拍照识题？**
做过取舍：OCR/公式识别要 35h，且公式识别错会把错题干送进检索，污染答案——**它不改善四个目标里的任何一条指标**。我们选择把同样的时间投在结构化切片与混合召回上，这两个直接决定 "答得对"。扫描件我们不做兜底，直接拒收并提示上传文字版，这比"识别个大概"更诚实。

**Q9 和市面上的 AI 搜题 App 有什么区别？**
它们用题库匹配，答案固定；我们做**基于用户自有资料的检索增强**——老师讲义、校本教材、个人笔记都能成为依据，答案带页码引用，这是"教辅 App"做不到的。

**Q10 三人怎么协作的？**
按数据流切三段，用两个契约（ChunkMetadata / OpenAPI）解耦；契约第 1 周冻结，前端靠 mock 并行；每周五集成日，CI + smoke 兜底；每人可备份他人模块（单点风险表）。

**Q11 项目最大的难点？**
不是调 API，是**数学内容的切分与检索**：公式必须与文字绑定、例题不能被拆、符号检索要精确。我们为此做了公式保护切分 + BM25 混合召回，这是本项目真正的工作量所在。

**Q12 如果给你更多时间，下一步做什么？**
① 拍照识题：用 VLM 直接读题图，替代传统 OCR 链路（本次因准确率与成本砍掉）；② 相似题与知识点标签：需要标注数据，本次未做；③ 答案可验证：接 SymPy 对推导结果做符号校验；④ 错题本与掌握度建模。

## 2.1 范围收缩的统一话术（被问"是不是功能太少"时用）

> "我们主动砍掉了 9 个功能，判据只有一个：删掉它，四条验收指标里有没有一条会下降。拍照识题、相似题、标签、个性化都过不了这条线，而且加起来要 90 多个小时——同样的时间放在结构化切片和混合召回上，能把 Recall@5 从 0.7 拉到 0.85。这是一个三人组在 10 周里能端到端交付、且每条指标都能复现的选择，不是能力不足。"

7. 难点二：混合召回 + RRF + Rerank（消融柱状图）
8. 难点三：幻觉控制四层防线
9. 工程：SSE 流式 + 公式渲染 + 一键部署
10. 数据：评估表 + 性能表
11. 演示截图 / 视频

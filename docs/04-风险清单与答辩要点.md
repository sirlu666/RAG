## 2. 答辩必问 12 题 · 参考答法

**Q1 为什么要 RAG，不直接微调？**
微调解决"说话风格/领域语感"，不解决"知不知道这本教材第 132 页怎么写的"。本项目核心诉求是可溯源、可更新、低成本：RAG 换一份教材只要重新入库，微调要重训；且数学答案需要引用原文作为可信依据，微调的参数里拿不出引用。

**Q2 你怎么证明检索有效？**
自建 200 题测试集（问题 + 标准答案 + 依据 chunk_id），指标 Recall@5、MRR；做了消融：纯向量 0.72 → +BM25 混合 0.81 → +Rerank 0.87（填真实数据）。评估脚本可复现，配置写在 `eval_runs.config`。

**Q3 chunk 大小怎么定的？**
不是拍的。做了 300/500/800 三档对比实验，Recall@5 分别为 …，最终选 500±200，并且因为数学的语义单元是"一道例题"，采用结构化切分优先、长度切分兜底。

**Q4 混合召回怎么融合分数？**
用 RRF（Reciprocal Rank Fusion, k=60），只依赖排名不依赖分数尺度，避免 BM25（0-20 分）与余弦（0-1）量纲不一致的问题；融合后再用 bge-reranker 精排 Top-20。

**Q5 怎么防止模型胡说？**
四层：① 检索门槛（top score < 阈值直接拒答）；② Prompt 约束（只能基于片段、必须标引用、公式用 LaTeX）；③ 后处理校验（答案中 `[n]` 必须存在）；④ 前端展示引用片段并可跳原文，用户能自查。

**Q6 多轮对话怎么做的？**
保留最近 N 轮 + 追问改写：把"这一步为什么"结合上一轮问题改写成独立 query 再检索，否则向量检索会失焦。上下文不塞满，避免 token 爆炸。

**Q7 系统并发能力如何？**
单机 2C4G，SSE 长连接 5 并发下首 token P95 ≈ …ms，端到端 ≈ …s。瓶颈在大模型 API 而非本地；本地检索 < 300ms（用缓存后 < 50ms）。

**Q8 OCR 公式识别准确率多少？**
文本 8x%，行内公式约 7x%（都填真实值），因此设计成"识别 → 用户可编辑确认 → 再提问"，把不确定性交给人确认，而不是假装 100%。

**Q9 和市面上的 AI 搜题 App 有什么区别？**
它们用题库匹配，答案固定；我们做**基于用户自有资料的检索增强**——老师讲义、校本教材、个人笔记都能成为依据，答案带页码引用，这是"教辅 App"做不到的。

**Q10 三人怎么协作的？**
按数据流切三段，用两个契约（ChunkMetadata / OpenAPI）解耦；契约第 1 周冻结，前端靠 mock 并行；每周五集成日，CI + smoke 兜底；每人可备份他人模块（单点风险表）。

**Q11 项目最大的难点？**
不是调 API，是**数学内容的切分与检索**：公式必须与文字绑定、例题不能被拆、符号检索要精确。我们为此做了公式保护切分 + BM25 混合召回，这是本项目真正的工作量所在。

**Q12 如果给你更多时间，下一步做什么？**
① 多模态直接读题图（VLM 替代 OCR 链路）；② 错题本 + 知识点掌握度建模（个性化推荐）；③ 生成解题步骤的可验证性校验（符号计算器 SymPy 交叉验证答案）。

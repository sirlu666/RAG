# 03 · 三人分工与协作规范

## 1. 分工原则

不是"按文件切"，而是**按数据流切段**：A 负责"把资料变成可检索的块"，B 负责"把块变成可信的回答"，C 负责"把回答变成人愿意用的产品"。
三段的交接物是两个契约（`ChunkMetadata`、`OpenAPI`），**契约稳定，内部自由**。

## 2. WBS（可执行任务级）

### A · 知识工程与数据处理

**目标**：任意一份数学资料，30 秒内变成高质量、可检索、可引用的 chunk。

| # | 任务 | 阶段 | 产出物 | 验收标准 |
|---|---|---|---|---|
| A1 | 语料采集与清洗 | P0 | `knowledge/raw/*`、`scripts/clean.py` | 20 页样本人工检查无乱码/断行 |
| A2 | 多格式解析器 | P1 | `services/parsing/{pdf,docx,md,txt}.py` | 统一输出 `Document{blocks[]}`（含页码/样式） |
| A3 | 噪声清洗 | P2 | `services/parsing/cleaner.py` | 页眉页脚/页码去除率 > 95% |
| A4 | 结构化识别 | P1-P2 | `services/parsing/segmenter.py` | 例题/习题/定理段落识别准确率 > 85%（抽 50 段人工核） |
| A5 | 公式保护切片器 | P1 | `rag/splitter.py` | 1000 次随机切片，0 次切断 `$...$`（单元测试覆盖） |
| A6 | 切片策略调参 | P2 | 实验记录（300/500/800 三档对比） | 给出"哪档 Recall@5 最高"的结论 |
| A7 | Embedding 与入库 | P1 | `rag/embedder.py`、`rag/indexer.py` | 1000 chunk < 3 min；批量 + 失败重试 |
| A8 | 增量更新与删除 | P2 | `reindex` 接口、`content_hash` 去重 | 同文件重传不产生重复 chunk |
| A9 | 扫描件 OCR | P2 | `services/ocr.py`、`/chat/ocr` | 扫描页识别率 > 80%，公式转 LaTeX 可渲染 |
| A10 | 自动打标签 | P3 | `services/tagger.py`（大模型批量） | 500 chunk 打标成本 < 1 元，人工抽检准确率 > 80% |
| A11 | 知识库版本管理 | P2 | 文档删除 → 向量同步删除 | 删除后检索不到残留（写断言测试） |

**A 的技术难点（答辩要讲）**
1. **公式不被切断**：用占位符法——先把 `$...$`/`$$...$$`/`\begin{}` 替换为 `@@MATH_i@@`，切完再还原；比写复杂正则安全。
2. **PDF 断行与排版**：PyMuPDF 按 block 取，行尾无标点且下行非编号 → 合并；双栏排版按 x 坐标分区再拼接。
3. **chunk 粒度权衡**：太小 → 例题被拆、上下文丢失；太大 → 向量语义被稀释。实验数据说话。

### B · RAG 引擎与大模型应用

**目标**：Top-5 里有依据，回答分步、有引用、不瞎编。

| # | 任务 | 阶段 | 产出物 | 验收标准 |
|---|---|---|---|---|
| B1 | 大模型客户端封装 | P0 | `rag/llm.py` | 统一 `chat(stream=True)`，超时 3 次退避重试，token 统计 |
| B2 | Chroma 检索封装 | P0 | `rag/retriever.py` | `search(query, kb_ids, top_k, where)` 返回统一 `Hit` |
| B3 | 基础 pipeline（纯向量） | P1 | `rag/pipeline.py` | 输入问题 → 输出 answer + citations |
| B4 | Prompt 体系 | P1-P2 | `rag/prompt.py`（system + 3 套 few-shot） | 方程/函数/证明各 10 题人工评审合格率 > 80% |
| B5 | 流式输出 + SSE 协议 | P1 | `/chat/stream` | 事件序列严格符合 `01` §6 |
| B6 | 混合召回 + RRF | P2 | `rag/hybrid.py`（jieba + rank_bm25） | 消融实验：Recall@5 提升 ≥ 5pt |
| B7 | Rerank | P2 | `rag/reranker.py` | Top-20→5，MRR 提升可测 |
| B8 | 拒答与置信度 | P2 | 阈值策略 + 兜底话术 | 20 个"库外问题"中 ≥ 16 个明确说"未找到依据" |
| B9 | 多轮与 query 改写 | P2 | `rag/memory.py` | "这一步为什么这样变形"能正确指代上一轮 |
| B10 | 引用与相似题 | P3 | citations 组装、`/chat/similar` | 引用能定位到 page；相似题不重复原题 |
| B11 | 评估体系 | P3 | `scripts/eval.py`、测试集 200 题 | 输出 Recall@5 / MRR / 正确率 / P95 延迟 |
| B12 | 缓存与限流 | P4 | 相同 query 缓存、slowapi | 重复问题 P95 延迟 < 300ms |

**B 的技术难点（答辩要讲）**
1. **为什么混合召回**：符号精确匹配（BM25 强）+ 语义泛化（向量强），RRF 免归一化。
2. **幻觉控制三层**：检索门槛（不达标拒答）→ Prompt 强约束（只能用给定片段、必须标注引用序号）→ 后处理校验（答案里的 `[n]` 必须存在于 citations）。
3. **多轮改写**：把"这一步为什么"用小模型/规则改写为独立问题再检索，否则向量检索直接失效。
4. **评估方法论**：LLM-as-judge + 50 题人工双盲抽检校准，报告里要写清 judge prompt 与一致性（Kappa 或一致率）。

### C · 系统平台与交互体验

**目标**：能登录、能上传、能流式看、公式不乱、手机上也能用、一条命令部署。

| # | 任务 | 阶段 | 产出物 | 验收标准 |
|---|---|---|---|---|
| C1 | 前端脚手架 | P0 | Vite + TS + Element Plus + 路由 + Pinia | `pnpm dev` 一键起，`/api` 代理通 |
| C2 | 登录注册页 | P1 | `views/LoginView.vue` | 表单校验、token 持久化、401 自动跳登录 |
| C3 | 对话页（核心） | P1-P2 | `views/ChatView.vue` | 流式打字机、停止生成、滚动跟随、多会话切换 |
| C4 | Markdown + KaTeX 渲染 | P1 | `components/MarkdownRenderer.vue` | 行内/块级公式、代码高亮、XSS 过滤 |
| C5 | 引用卡片与原文跳转 | P3 | `components/CitationCard.vue` | 点引用 → 预览页高亮对应 chunk |
| C6 | 上传与进度 | P1-P2 | `components/DocUploader.vue` | 拖拽、类型/大小校验、进度条、失败重试 |
| C7 | 知识库管理 | P2 | `views/KbView.vue` / `DocView.vue` | 建/删库、文档列表、预览、删除、重建索引 |
| C8 | 图片提问 | P3 | 裁切 + 调 `/chat/ocr` + 可编辑确认 | 识别失败可手输，不阻塞流程 |
| C9 | 历史与反馈 | P3 | 会话列表、点赞点踩 | 刷新后历史还在 |
| C10 | 个性化与响应式 | P3 | 主题色/深色/字号/头像 | 320px 宽度可用 |
| C11 | 部署 | P4 | `deploy/*`、Dockerfile | 一键起，SSE 正常（重点：关 buffering） |
| C12 | 异常与错误码映射 | P2-P4 | `api/http.ts` 统一处理 | 每个错误码有中文文案 |

**C 的技术难点（答辩要讲）**
1. **SSE 手写解析**：`EventSource` 不支持 POST + JWT Header，必须 `fetch` + `ReadableStream` + `TextDecoder`，按 `\n\n` 分帧。
2. **渲染性能**：流式 token 逐个 setState 会卡，用 buffer + rAF 批量 flush；公式多的消息用 `v-memo`。
3. **KaTeX 与 Markdown 的顺序**：先保护公式（占位符）再渲染 Markdown 再还原，否则 `_` `*` 会把公式打乱。
4. **部署坑**：Nginx `proxy_buffering off`、`proxy_read_timeout 300s`、`X-Accel-Buffering: no`，否则"流式变成一次性返回"。

## 4. Git 规范

```
main           ← 只接受来自 dev 的 PR，随时可部署
 └ dev         ← 集成分支，周五集成日合并
    ├ feat/a-splitter-structured
    ├ feat/b-hybrid-retrieval
    ├ fix/c-sse-parse
    └ chore/all-deploy
```

- 分支命名：`<type>/<owner>-<subject>`；`type ∈ feat|fix|refactor|chore|docs`
- 提交信息（Conventional Commits，中文正文可）：
  `feat(rag): 支持 BM25+向量 RRF 融合召回`
- PR 规则：≤ 400 行改动；必须 1 人 review（跨人 review：A 的 PR 由 B 看，B 的由 C 看，C 的由 A 看）；CI 绿才可合。
- **禁止**：直接 push `main`；提交 `.env`、`data/`、`*.db`、语料大文件（用 Git LFS 或网盘）。
- 每天下班前 push 到自己的 feature 分支（哪怕没写完，写 `WIP:` 前缀）。

## 5. 代码与工程规范

| 项 | 规范 |
|---|---|
| Python | ruff + black（行宽 100）；类型注解必填（public 函数）；异常用自定义 `AppError(code, msg)` |
| TS/Vue | eslint + prettier；`<script setup lang="ts">`；组件 PascalCase；API 调用集中在 `src/api/` |
| 日志 | 结构化：`logger.info("retrieval", extra={"q": q, "hits": n, "ms": t})`，禁止 print |
| 配置 | 全部走 `core/config.py`（pydantic-settings），禁止硬编码 key / 路径 |
| 密钥 | `.env` 本地，`.env.example` 入库；上线用环境变量注入 |

## 6. 沟通与冲突处理

- **技术分歧**：24 小时内用"1 页纸对比（方案/成本/风险）+ 跑个小实验"决定，谁提议谁举证；仍不一致由 C（集成负责人）拍板。
- **进度落后**：立即在群里说 + 按 `02` §8 的砍单顺序降级，**不许默默延期**。
- **被打断**：任何人可以随时拉着对方看 5 分钟代码，但不许直接改别人分支。
- **轮值**：每周一人当"集成负责人"（A→B→C 轮），负责周五合并、跑 smoke、更新进度表。

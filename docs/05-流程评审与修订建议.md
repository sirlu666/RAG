# 05 · 流程评审（批判性）与修订建议

> **状态：历史记录（v1 评审）。** 评审后团队采纳了更彻底的处理方式——不是"延后/降级"，而是按 `06-范围基线.md` 把 9 项非目标功能直接删除。
> 因此本文件的 §5 排期 v2、§8 修改清单中的章节号与字段名对应的是 v1 文档；**现行口径以 00–04 的 v2.1 与 06 为准**。
> 保留本文件的原因：其中的问题证据、工作量核算方法与 pre-mortem 结论仍然有效，答辩被问"你们怎么排的期"时可直接引用。

> 评审人视角：如果我是甲方/答辩评委，拿着这份计划能不能验收？
> 评审对象：`docs/00`–`docs/04`、目录骨架、21 个接口、55 条 WBS 任务。
> 方法：① 依赖拓扑找关键路径 ② 工作量 vs 产能 ③ 验收标准可执行性 ④ 契约完整性 ⑤ pre-mortem（假设项目已经失败，倒推原因）。

## 0. 结论先说

**技术路线可行，排期与验收标准不可行。**

- 工作量核算后缺口 **30–80 人时**，且高度集中在 C（190h，超载约 60h）和 A 的 OCR 分支（35h）。
- 计划里 **0 天缓冲**，同时又规定"Gate 不通过不进入下一阶段"。这两个设定放在一起是自相矛盾的，实际结果一定是"Gate 形同虚设"或"造假 DoD"。
- 20 个接口、5 篇文档、55 个任务都写了，但**最关键的三个东西没有定义**：语料可用性验收、评估集的标注流程、SSE 的类型化契约。
- 按现状执行，最可能的结局是：**第 9 周能演示，但指标拿不出来、功能砍掉 3 项、答辩靠讲故事**。这不是技术能力问题，是排期结构与验收口径问题。

下面按"必须改 / 应该改 / 可以忍"分级。每条都给出**证据位置**，避免空泛。

## 1. P0 级：不改就会出问题

### P0-1 "垂直切片"并不窄，登录被塞进了 P1

**证据**
- `00 §3` MoSCoW 把"登录注册 + JWT + 个人知识库隔离"列为 **P1 Must**。
- `02 §2` 同一阶段却写"**不管权限细节**"。
- `02 · W5` 的实际排期里才出现"JWT 全链路"。
- `02 §0` 的阶段目标写"不流式"，而 `W3` 又排了"接 SSE 流式"。

一份文档里三处互相矛盾，说明这一版计划是"按理想顺序写的"，不是"按依赖排的"。

**后果**
C 在 W2 要同时交付：上传组件、文档列表、会话页、流式渲染、登录。登录不是"加个表单"，它连带 token 刷新、401 拦截、路由守卫、匿名态 UI 分支，实测 20h 起。C 在 P1 就会掉队，而 C 是整条链的出口。

**修法**
P1 明确为**匿名单库 MVP**：不登录、不建库、不传 PDF、不做进度条。登录整体后移到 P2 末。匿名态的 UI 分支先用 `useUser()` 空实现占位，避免后面返工。

### P0-2 关键路径的起点没有被验收：语料

**证据**
`02 · Gate 0` 的验收是"git clone 能跑 / `/docs` 接口全 / 对话页能流式打印假回答"——全是**代码侧**指标，没有一条关于**数据侧**。

**后果**
如果拿到的教材是扫描版、加密 PDF、双栏排版或竖排，A 在第 2 周就卡死，B 无 chunk 可测，C 无内容可看。而这个问题要到第 4 周才暴露（因为 P1 只用 md 自造数据）。**这是全项目最大的单点，却恰好没有检查点。**

**修法**
Gate 0 增加一条硬指标：**任选 1 本目标教材，解析后 ≥ 5 万汉字、随机抽 5 页人工确认无乱码/无错序、能识别出 ≥ 30 个"例 N"**。不达标就换语料来源（找电子版/换出版社/换学科），不许带病进 P1。

### P0-3 没有缓冲 + 硬 Gate = 催生"造假 DoD"

**证据**
`02 §0`："每个阶段最后一天必须满足 DoD，否则不进入下一阶段"；W1–W10 排满，0 天余量；`04` 的风险表里 10 条风险，但 R4（进度不同步）的对策只是"每周五集成日"。

**后果**
学生只有两种反应：① 无视 Gate 继续往下（Gate 变成摆设）；② 把没做完的写成"已完成，后期待优化"（进度表失真）。两种都会让第 6 周之后的计划彻底失去参考价值。

**修法**
- Gate 改为**决策点**，三选一：通过 / 降级（砍哪一项，预先写死）/ 延期（吃 W9 缓冲）。
- **W9 整周设为缓冲**：只修 bug、只做部署复跑，不接任何新功能。谁想往 W9 塞功能，必须先在群里砍掉等量的东西。

### P0-4 评估集的"生产过程"根本不存在

**证据**
- 目标写死 Recall@5 ≥ 0.85、正确率 ≥ 0.80（`00 §1`）。
- 但全文只有 `02 · P3` 一行："评估集 B（A 供语料，C 做标注表）"。
- 没有标注工具、没有标注规范、没有 gold chunk 的获取方式、没有一致性检验、没有判定口径。

**后果**
① 200 题 × 人工找"正确依据 chunk"，20–30 小时，没人有这个时间；② B 自己出题、自己调参 → 对自己造的测试集过拟合，答辩一问"测试集谁标的"就露；③ "正确率"谁判、判几次、两次不一致算谁的，全没定义。

**修法**（三步，成本降一个量级）
1. **反推出题**：从已入库 chunk 反向出题（给一段教材，让大模型生成 1 个问题 + 标准答案，人工只做"通过/不通过"），gold chunk 天然存在，省掉查找成本。
2. **规模降到 80 题**，先跑通 40 题闭环。
3. **口径固定**：temperature=0、top_k 固定、embedding 版本固定、judge prompt 版本化、每题跑 3 次取均值；抽 20 题双人交叉判定，报一致率。

## 2. P1 级：显著风险，本周就该处理

### P1-1 越权读取（安全漏洞，且就在契约里）

**证据**
`01 §3` 的过滤模板只有 `{"kb_id": {"$in": kb_ids}}`，`kb_ids` 直接从请求体来，**没有任何 user_id 归属校验**。

**后果**
任何登录用户传别人的 `kb_id`，就能读到他人私有资料的内容并让它出现在回答里。答辩现场被问一句"你怎么保证 A 看不到 B 的资料"就答不上来。

**修法**
检索前强制 `kb_service.assert_readable(user_id, kb_ids)`；未登录只允许 `["public"]`；补一条单测："用户 A 传用户 B 的 kb_id → 403 或静默剔除"。

### P1-2 单进程三件套的并发假设，没有验证过

**证据**
`00 · ADR-05` 断言"单机、低并发（3–5 人），BackgroundTasks 足够"，但没提 SQLite 写锁与 Chroma 的并发写。

**后果**
上传解析（写 chunks + 写向量）与问答（写 messages + 读向量）并发时：SQLite 默认 journal 模式会 `database is locked`；Chroma PersistentClient 在 Windows 上多线程写入容易抛锁错误。演示时"点上传，问答就卡住"是最难解释的故障。

**修法**
① SQLite 开 WAL + `timeout=30`；② 入库写操作加进程内单写锁；③ 同一时刻只允许 1 个入库任务（DB 标记 + 前端排队文案）；④ 在 `00 §7` 补一条"为什么 `--workers 1`"。

### P1-3 唯一没有类型化的契约，恰好是最核心的

**证据**
OpenAPI 覆盖 20 个 JSON 接口；SSE 的 5 类事件（meta / citation / delta / done / error）是手写字符串，`docs/api/README.md` 只放了 mock 文本。

**后果**
C 生成的 TS 类型里没有 SSE 事件；B 把 `doc_name` 改成 `documentName`，编译期零报错，运行时页面空白。**最核心的接口，保护最弱。**

**修法**
`schemas.py` 定义 5 个事件模型；写一条契约测试：读 `mock/chat_stream.txt` → 逐帧 `model_validate` → 断言字段齐全。mock 文件从此变成"可执行契约"，改坏就红。

### P1-4 "停止生成"没有服务端语义

**证据**
`frontend/README` 与 `02 · P2` 都排了停止按钮；`01` 只写"P4 可选做 stop 接口"。

**后果**
现状实现只能是：前端 abort → 后端继续生成 → 落库半截回答 → 用户重发 → 历史里两条，且 token 白烧。

**修法**
要么 P2 就定协议（`client_msg_id` + `cancelled` 状态），要么**明确不做**、把按钮删掉。最糟的是留一个语义模糊的按钮。

### P1-5 CI / 依赖锁定 / 环境统一：有词无活

**证据**
`02 · D4` 只有一句"仓库/CI/环境统一"，无 owner、无产物；`requirements.txt` 全是范围版本；前端未提交 lockfile 策略；三个人的操作系统未统一。

**后果**
"我这儿能跑"会在第 5 周集中爆发，而排查环境问题的成本（chromadb/hnswlib 在 Windows 需要 VS Build Tools、PyMuPDF 版本差异、Node 版本差异）远高于当初配置一次的成本。

**修法（全项目性价比最高的一件事，1 天）**
C 在 W1 交付：`.github/workflows/ci.yml`（ruff + pytest + vue-tsc + build）、`uv lock` 或 `pip-compile` 产出锁定文件、提交 `pnpm-lock.yaml`、新增 `docs/环境清单.md`（Python 3.11 / Node 20 / Windows 需 Build Tools / 可选 WSL2）。

### P1-6 部署只留 1 天

**证据**
`02 · P4` 把 Docker 部署放在 W9 D4，只留一天。

**后果**
slim 镜像上装 chromadb / PyMuPDF / bcrypt 需要编译依赖，首次 `build` 失败 2–5 次是常态；`nginx.conf` 挂 `../frontend/dist` 但 compose 里没有前端构建步骤（`pnpm build` 得手工先跑）。

**修法**
W6 先做一次"从零 build"演练（只做 backend 镜像 + 静态托管），把坑提前踩掉；W9 只做复跑。compose 增加一个 `frontend-build` stage 或在文档里写死"先 build 再 up"。

## 3. P2 级：会拖慢，但不致命

| # | 问题 | 证据 | 修法 |
|---|---|---|---|
| S-1 | **文档过重** | 5 篇 ~1500 行；按每周 2h×3 人维护 ≈ 60h，等于一个模块的工作量 | 合并为 3 篇（00 并入 01、04 并入 03）；每周五只同步"契约 + 排期"两种信息；细节交给 docstring |
| S-2 | **PR ≤400 行不现实** | `03 §4`；而"切片器 v2"必然 600+ 行 | 改为"按可独立验证的功能切 PR；大 PR 必须附 eval 指标 + 拆开的 commit" |
| S-3 | **OCR 责任交叉** | `01` 里 `/chat/ocr` 归 A；`02 · W5` 让 B 接"拍照→OCR→检索"；C 做 UI | 指定**拍照链路 owner = A**，B 只提供检索接口，C 只提供页面；一条链路只能有一个负责人 |
| S-4 | **成本无预算** | 200 题评估 + 800 chunk 嵌入 + OCR 调用 | 估算：DeepSeek 单轮全量评估约 5–15 元；embedding 可忽略；Mathpix 约 $0.004/页 → 用免费额度或 PaddleOCR，避免"跑到一半没钱" |
| S-5 | **评估不可复现** | `eval_runs.config` 有字段，但没规定固定 temperature / top_k / 模型版本 | 全部写进 config；每题跑 3 次；报告里注明"可复现命令" |
| S-6 | **隐私与删除语义缺失** | `01 §2` 有软删字段但无删除流程 | 删库 = 软删记录 + 异步删向量 + 删文件 + 消息引用降级为"来源已删除"；写进接口 #7 的 DoD |
| S-7 | **匿名限流按 IP** | `01 §5` #3001"未登录每日 3 次" | 校园网 NAT 下整栋楼同 IP，会误伤；改"设备指纹 + IP"双维度，或只做全局限速 |
| S-8 | **Windows 现实未处理** | 项目在 `D:/WorkSpace`，团队大概率 Windows | demo 走"本地 uvicorn + `vite preview`"，Docker 只作为交付物与备用；WSL2 写进环境清单 |

## 4. 工作量核算：缺口是算出来的，不是感觉

估算口径：以"熟练学生 + 有 AI 辅助"计，含调试与自测，不含返工；误差 ±30%，只用于**相对比较**。

|---|---|---|

| A | 结构化识别（例题/习题/定理） | 20 |
| A | 切片器 + 公式保护 + 三档调参 | 18 |
| A | embedding + 入库 + 增量/删除 | 20 |
| A | **OCR（扫描件 + 公式）** | **35** |
| A | 自动打标签 | 12 |
| **A 小计** | | **140** |
| B | LLM 封装 + 重试 + 统计 | 8 |
| B | 检索封装 + 纯向量 pipeline | 15 |
| B | Prompt 体系 + 3 套 few-shot | 20 |
| B | SSE 流式 + 引用组装 | 15 |
| B | BM25 + RRF + Rerank | 23 |
| B | 多轮改写 + 拒答策略 | 18 |
| B | 相似题 | 6 |
| B | 评估脚本 + 80 题（含标注） | 35 |
| B | 缓存 / 限流 | 8 |
| **B 小计** | | **148** |
| C | 脚手架 + 路由 + 状态 | 10 |
| C | 登录注册 + JWT 全链路 | 20 |
| C | 对话页（流式 + Markdown + KaTeX） | 45 |
| C | 上传 + 进度 + 文档列表 | 18 |

**产能**：3 人 × 10 周 × 13h（课设强度）= **390h**；按 15h/周 = **450h**。
**缺口**：以 450h 计仍缺 **29h**；以 390h 计缺 **89h**。且 C 一人 191h，等于要求他每周 19h 连续 10 周不出状况——**这是计划里最脆的一环**。

**三刀补齐（不砍核心三件套）**

| 动作 | 省下 | 代价 |
|---|---|---|
| 砍公式 OCR，只保留"整题拍照 → 文字识别，用户可改" | −30h | 扫描版教材入库能力下降，写进"未来工作" |
| 登录与个人库后移到 P2 末，P1 不做权限 | −25h（C） | 第 3 周 Demo 是匿名态，答辩无影响 |
| 知识库管理页延到 P3，P2 只做"列表 + 删除" | −15h（C） | 少一个 CRUD 页面 |
| 评估题量 200 → 80 | −15h（B） | 指标置信度略降，但可跑 3 次补 |
| **合计** | **−85h** | 479 → 394h，勉强落在 390–450 之间，**留出约 10h 缓冲（仍然偏紧）** |

结论：**必须同时执行这四刀**，只砍一两项仍然超载。

## 7. 本周内必做（按性价比排序）

## 9. 我保留的三条意见（可能被反驳，先把理由放这）

1. **流式仍用 SSE**：如果 P3 真的要做"停止生成 + 边生成边追加提问"，SSE 会更别扭；但换 WebSocket 的代价（前端 1 天 + 后端 0.5 天）在 P3 仍可承受，不必现在换。
2. **仍用单 collection**：chunk 超过 5 万后，`where` 过滤叠加 HNSW 会有召回损失；本项目量级（≤1 万）没问题，但要在文档里写下"何时该分区"的阈值。
3. **仍是 10 周排期**：如果实际只有 8 周，请按 `02 §8` 做**整段压缩映射**，不要"删了功能却保留 10 周排期"——那会让所有缓冲凭空消失。
